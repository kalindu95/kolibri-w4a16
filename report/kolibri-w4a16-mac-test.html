Kolibri W4A16 pipeline on a MacBook

The FP8 → BF16 → GPTQ 4-bit → evaluation pipeline was run end to end twice on a 24 GB MacBook: once on the tiny random Kolibri-1 test model, and once on a real block-FP8 model, Qwen3-0.6B-FP8. This page reports memory and CPU use for every step, and how close the 4-bit Qwen3 model stays to the original.

Findings

What broke and what was changed

Fixed

GPTQ crashed on Qwen3 with the default damping

At dampening_frac=0.01, calibration stopped on model.layers.2.mlp.down_proj with linalg.cholesky: … not positive-definite. The failure is in the factorization of the inverted Hessian, which llm-compressor's round-to-nearest fallback doesn't cover. Damping 0.05 fixed it with no layers falling back. The script now has --dampening-frac (default unchanged at 0.01) and the README explains when to raise it.

Mac only

Loading a model onto the Mac GPU crashes step 03

03_compare_ppl.py loads with device_map="auto", which picks the Mac GPU (MPS). The process then dies silently with exit code −5. Loading on the CPU works, so step 03 ran through a small wrapper that forces CPU. On the intended NVIDIA machine this doesn't arise, and the script was left unchanged.

Passed

Tiny Kolibri-1 model, all steps

FP8 dequantization reproduced all 318 tensor names with about 2.6% relative error, which is FP8 rounding. GPTQ quantized all 275 linear layers including every expert and saved pack-quantized W4 group-128 tensors, and the result reloads and generates. Its perplexity numbers mean nothing because the weights are random.

Note

Dataset streaming left a process behind

The script that streamed calibration data wrote both files and then hung on exit, holding 2.4 GB. The live monitor showed it and it was stopped. This came from the test setup, not the pipeline.

Scope

What this test does and doesn't show

  • Qwen3-0.6B is dense. It exercises the real FP8 format, dequantization, GPTQ and the compressed-tensors output, but not Kolibri's 384-expert MoE path. That path was only checked on the tiny random model.
  • Small models lose more at 4 bits than large ones, so +4.4% perplexity at 0.6B is a pessimistic stand-in for 78B.
  • Peak memory scales with model size. The full Kolibri-1 needs about 156 GB for its BF16 weights and an NVIDIA GPU with about 30 GB free, so it can't run on this Mac. The README's rented H100 with 256 GB of RAM is still the plan.
  • The full-size run could hit the same Cholesky failure. If it does, add --dampening-frac 0.05 to step 2 in run_all.sh.
